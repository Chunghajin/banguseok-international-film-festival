# M4 — Supabase 저장·공개·소유자 관리

2026-10-21. v1.1의 G1 원본/공개 테이블·서버 전용 RPC·RLS를 M1~M3에 연결했다. SQL·기존 migration·환경 변수·의존성·설문/시상/특별상 규칙은 변경하지 않았다. 최초 저장은 비공개이며, 명시적 동의 후 공유 행을 만드는 문서의 규칙을 적용했다.

## 사용자 동선

- `/create/result`: 로컬 HTML 확인 → ‘내 영화제 개최하기’ → 익명 세션 확인/생성 → 서버에서 영화 ID·설문·특별상 재검증 → 비공개 저장.
- `/my`: 이 브라우저 소유 영화제 목록. GET은 새 익명 계정을 만들지 않는다.
- `/my/{id}`: 서버 저장본, 공개 동의, 공유 링크 생성·복사·갱신·중단, 로컬 재편집, 확인 후 삭제.
- `/f/{token}`: 인증 없는 읽기 전용 공개 HTML. 공개 스냅샷만 사용하고 소유자 메뉴를 렌더링하지 않는다.

로컬 주소는 `http://127.0.0.1:3000`이다. 공유 주소 형식은 `https://<배포 호스트>/f/<43자 조회 토큰>`이다. localhost 주소는 인터넷 공유 주소가 아니다. 실제 토큰은 보고서·로그·스크린샷에 남기지 않았다. 공개 화면 증거에서는 일부 포스터가 외부 이미지 실패 대체 타일로 표시되며 제목·연도·HTML은 유지된다.

수정 저장은 revision만 증가시키며 기존 공개본은 유지한다. ‘공유본 갱신’을 동의하여 실행해야 공개본이 갱신되고 같은 URL을 유지한다. 공개 중단은 공유 행 삭제, 재공개는 새 토큰이다. 삭제는 원본·공개 행 cascade이며 익명 Auth 계정이나 보존된 로컬 내용 자체를 삭제하는 기능은 아니다.

## 신뢰 경계

G1 클라이언트를 `src/lib/supabase-core.mjs`로 이동하고 기존 스크립트는 재수출하도록 했다. 제품은 `server-only` 서비스에서만 사용한다. Auth `/user`로 익명 사용자 확인 → RLS 소유 원본 조회 → 기존 owner/revision 조건 RPC·DELETE 순서다. service role은 RLS를 우회하므로 이 서버 검사와 기존 RPC 검사를 함께 유지한다.

서버 입력은 16KB JSON, UUID/revision/버전, 12 grapheme 닉네임, 설문 값, 고유 3~6부문과 양의 TMDB ID로 제한한다. client의 owner_id·result·제목·포스터 URL은 거부한다. 새 영화 ID는 실제 TMDB 상세로 확인하고 같은 ID의 기존 저장 snapshot은 유지한다. 특별상은 서버 규칙 함수로 다시 계산한다.

공개 데이터는 G1 RPC의 9개 필드 허용목록과 영화별 6개 필드를 사용한다. 원본 설문·owner·draft ID·내부 evidence는 공개 HTML에 포함하지 않는다. 공개 token을 인증 cookie로 제시해도 편집 권한이 생기지 않는다.

세션은 HttpOnly/SameSite=Lax cookie이며 HTTPS에서는 Secure를 붙인다. access 만료 시 서버 refresh를 사용하고 refresh token은 JSON·localStorage에 반환하지 않는다. 인증 정보는 의도한 Set-Cookie/Cookie 전송에만 사용한다. 브라우저 데이터 삭제·기기 변경 시 권한 상실 경고를 표시하고 복구를 약속하지 않는다.

API와 공개 HTML은 private/no-store, 공개 HTML은 noindex/no-referrer다. 공개 token이 요청 로그에 남지 않도록 Next 수신 요청 로깅을 껐다. 공개 중단/삭제 후 URL은 no-store 404다. 사용자가 이미 캡처한 화면·외부 SNS 캐시까지 회수하지는 못한다.

## 실패와 초안

중복 클릭을 잠그고 요청에 30초 제한을 둔다. 저장 실패는 로컬 초안을 삭제하지 않는다. 저장 성공 때 id/revision을 연결하고 저장 도중 새 로컬 편집은 덮어쓰지 않는다. 응답 유실 후 같은 draft 생성 재시도는 원본을 재사용한다. 수정 재시도는 정확히 한 revision 증가와 동일 입력인 경우만 합의하고 나머지는 409로 막는다.

오래된 편집 초안은 자동으로 최신 revision에 덮어쓰지 않는다. 서버 저장본으로 초안을 바꾸려면 명시적으로 확인한다. 다른 활성 로컬 초안을 교체할 때도 확인한다. 삭제 응답이 유실되면 인증된 재조회 404일 때만 완료로 정리하며, 401·409·서버 장애나 여전히 존재하는 원본은 성공 처리하지 않는다.

HTTP 실검증은 정상 저장·중복 재시도·위조 입력·미인증·B 접근·공개 token 편집 거부·9필드 snapshot·명시적 갱신·revision 충돌·서버 refresh·공개 중단·재공개·cascade 삭제·Origin 거부를 확인했다. Chrome은 실제 버튼·clipboard·별도 A/B context·새로고침·M1 재편집·저장·이전 공개본 유지·갱신·중단·삭제를 확인했다. 임시 Auth 사용자/영화제는 finally에서 정리했다.

503 저장 응답과 DELETE 응답 유실은 브라우저 오류 주입이다. 삭제 자체와 재조회·DB 제거는 실제 요청이다. 오래된 로컬 revision은 fixture로 주입하고 실제 확인 UI를 조작했다. HTTP 409는 실제 DB 요청이며 동시 네트워크 경합 부하 시험은 아니다. CAPTCHA·실제 기기·Vercel 검증으로 간주하지 않는다.

처음 실행에서는 Node TMDB 요청이 timeout되고 G2 9건/G3 5건이 실패했다. 개발 서버 재시작 후 Chromium의 초기 로딩 대기도 정상화했다. Node 주소 선택을 IPv4 우선/자동 family 선택 비활성으로 실행한 최종 검사에서는 전부 통과했다. 앱의 timeout·접근 제어는 완화하지 않았다. 이 로컬 네트워크 조건은 배포 환경에서 다시 확인해야 한다.

```sh
NODE_OPTIONS='--no-network-family-autoselection --dns-result-order=ipv4first' npm run dev -- --hostname 127.0.0.1
# 별도 터미널, 전용 테스트 Supabase 프로젝트에서만 실행
NODE_OPTIONS='--no-network-family-autoselection --dns-result-order=ipv4first' G1_ALLOW_TEST_WRITES=yes npm run verify:m4
NODE_OPTIONS='--no-network-family-autoselection --dns-result-order=ipv4first' G1_ALLOW_TEST_WRITES=yes npm run verify:m4:browser
```

## 배포 차단 및 남은 검증

**운영 영화 API의 503 보호를 유지했다. M4의 세션 생성·저장·게시·공개 중단·삭제도 production에서 503으로 차단한다.** 관리형 요청 제한·CAPTCHA·사용량/비용 한도 확인 전에 인터넷 쓰기 API를 공개하지 않는다. 현재 구현은 실제 Supabase를 사용한 로컬 통합 완료이며 운영 배포 완료가 아니다.

로컬 signup 10회/분, 소유자 쓰기 60회/분, 저장 10회/시간은 단일 프로세스 한도다. 분산 환경 보호가 아니며 CAPTCHA 위젯도 아직 없다. 운영 보호와 제공자 설정, 외부 호스트 origin 정책, HTTPS cookie/refresh 경합, Vercel 캐시·로그/플랫폼 요청 URL 수집을 검증한 뒤 별도 작업으로 게이트를 열어야 한다. Next 로그를 꺼도 호스팅 제공자 로그 설정까지 바뀌지는 않는다.

실제 스마트폰/Safari·스크린리더·다중 서버 refresh 경합·만료까지의 장기 세션·배포 호스트 공개 URL·실제 동시 수정 부하는 미검증이다. service-role 유출은 여전히 전 데이터 위험이다. PNG/CSV/계정 복구/회원가입/커뮤니티/고급 OG는 구현하지 않았다. HTML 저장·공개에는 PNG endpoint 의존성이 없다.
