# 방국제 PRD v1.1

작성일 2026-10-20 · 기술 검증 10/21 · 출시 목표 10/27 · 제출 10/28

상태: **개발 착수용 명세, 사용자 최종 승인 전**. 이번 작업은 문서 개정이다. 앱 구현·외부 서비스 설정·배포·사용자 테스트는 하지 않았다. 사용자가 v1.1을 기준으로 개발하라고 지시하면 승인된 기준으로 기록한다.

## 0. 문서 체계와 결정 상태

저장소 루트 기준 `docs/PRD.md`, `docs/SCREEN_CONTENT.md`, `docs/CODEX_STEPS.md`, `docs/CHANGELOG.md`를 함께 읽는다. Mac 절대경로나 v1.0 파일을 개발 프롬프트의 입력으로 사용하지 않는다. 같은 내용의 한국어 파일명 v1.1은 전달용 스냅샷이다. 수정은 docs에서 먼저 하고 전달본을 동기화한다.

- **[유지]** 사용자 지정 브랜드와 v1.0에서 유지하라고 한 설계.
- **[반영]** 이번 수정 요청에 따른 변경.
- **[명세 선택]** 요청을 구현 가능하도록 구체화한 기본값. 사용자 최종 승인과 구분한다.
- **[가설]** 실제 사용자 테스트 전인 UX·편집 판단.
- **[검증 게이트]** 개발 중 증거로 통과해야 하는 항목.

문항/콘텐츠/규칙의 단일 기준은 SCREEN_CONTENT 2~7장, 데이터/보안/우선순위의 단일 기준은 PRD다. CODEX_STEPS는 이를 실행 순서로 참조한다. 상충하면 임의로 골라 개발하지 말고 CHANGELOG에 충돌과 해결 내용을 남긴다.

버전 계약: `spec_version=1.1`, `draft_version=draft-v1.1`, `survey_version=survey-v1.1`, `catalog_version=awards-v1.1`, `rules_version=result-v1.1`. 문구 수정도 출력에 영향을 주므로 rules_version을 올린다.

**R11 PNG**: 10/21에 한글 PNG를 검증하고, 성공하면 1080×1920 기본 결과 이미지 저장을 구현한다. 원격 포스터 실패는 제목 타일로 대체한다.

## 3. 변하지 않는 사용자 규칙 [유지]

1. 영화만 선택한다. 평생공로상도 배우/감독이 아닌 영화 한 편이다.
2. `grand, lifetime, sorry, once, dissent, rescue`의 고정 순서·6부문. 최소3개의 서로 다른 부문이 있으면 완성한다. 대상도 선택 사항이다.
3. 동일 영화의 복수 부문 수상 허용. 한 편을 세 부문에 골라도 가능하다.
4. “지금까지 실제로 본 영화 중 골라 주세요.”를 선정 화면에 표시한다. 올해0편이어도 과거 관람작으로 참여한다.
5. 후보 노출·CSV 별점·검색만으로 관람 사실이나 수상을 자동 확정하지 않는다.
6. 건너뛰기·미선정은 미관람이라는 뜻이 아니다. 전체 부문 방문을 강요하지 않는다.
7. 설문/선정은 로컬 임시 저장, 결과 완성 시 DB 저장. 최초 저장은 비공개다.
8. 공개 링크는 조회 전용이다. 수정/삭제는 로그인 화면 유무와 관계없이 서버 소유권 검증이 필요하다.
9. 특별상은 고정 규칙/템플릿만 사용하며 관람량으로 우열을 매기지 않는다.
10. 수상 이유 자유 입력, 추가 상2종은 이번 범위에 넣지 않는다.

## 4. 무작위 후보와 로컬 상태 [반영]

### 4.1 후보 풀

부문별12편을 편집 데이터로 둔다. `familiar(넓은 인지도 예상)`, `cine(애호가 인지도 예상)`, `discovery(의외성 예상)`에 **각4편**을 배정한다. 한 부문 안에서 ID 중복 금지, 다른 부문 사이 중복은 허용한다.

분류는 한국어권 잠재 사용자에 대한 편집 가설이다. 관람 통계·흥행 순위·개인 이력 추정이 아니다. 후보는 이미 본 영화를 떠올리는 단서이지 새 영화를 반드시 보라는 추천이 아니다.

### 4.2 층화 무작위 배치 [명세 선택]

새 초안 생성 시 각 부문에 대해 다음을 **한 번만** 수행한다.

1. 세 그룹의 4편을 각각 Fisher–Yates 방식으로 섞는다. 편향된 `sort(random)` 방식은 쓰지 않는다.
2. 각 그룹의 앞2편씩을 모아 페이지0의6편을 만들고, 이6편의 표시 순서도 섞는다.
3. 각 그룹의 뒤2편씩을 모아 페이지1을 만들고 동일하게 섞는다.
4. 두 페이지를 이어 붙인 `candidate_order[category_id]` 12개 ID와 `candidate_page=0`을 로컬 초안에 저장한다.

이로써 정상12편일 때 두 화면 모두2:2:2를 만족한다. 완전 무제약 셔플 대신 이 방식을 선택한 이유는 **무작위 배치와 친숙도 가설을 동시에 적용하기 위해서**다.

랜덤성은 플랫폼 난수로 셔플을 한 번 생성하는 데만 사용한다. 결과지 계산에는 draft_id·후보 순서·난수를 넣지 않는다. 서로 다른 초안의 순서는 우연히 같을 수 있으며 강제로 다르게 만들지 않는다.

### 4.3 상태 전이

- ‘다른 후보 보기’: page0→page1. 이후 라벨 ‘처음 후보 다시 보기’: page1→page0. 이미 본 전체 후보 수를12로 설명하고 무한 추천을 암시하지 않는다.
- 새로고침/뒤로 이동/검색 닫기: 배열, 페이지, 확정작, 미확정 선택을 복원한다.
- 새 초안: 새 draft_id와 새 후보 배열. 기존 DB 영화제는 유지한다.
- 저장된 영화제 수정 진입: 해당 영화제에 연결된 로컬 편집 초안이 있으면 재사용한다. 없으면 새 편집 초안 후보 배열을 만들되 저장된 수상작은 그대로 유지한다. 후보 배열 자체는 서버 결과의 일부가 아니다.
- catalog가 바뀌어도 유효한 기존 배열은 재셔플하지 않는다. 해당 초안의 catalog_version을 유지한다. 저장된 선택작은 TMDB 검색작과 동일하게 처리한다.
- 중복/변조/길이 오류의 후보 배열만 다시 만든다. 설문과 수상작은 보존하고 “후보 목록을 복구했어요” 표시.
- 정상12편 미만인 장애: 같은 그룹 대체가 가능하면 미노출된 유효 ID를 사용하고 수정 배열을 저장한다. 모든12편이 이미 배열에 있으므로 예비가 없으면 **해당 슬롯을 정보 없음으로 표시**한다. 다른 페이지 작품을 복제하지 않는다. 검색은 계속 가능하다.
- 이미지가 없다는 이유만으로 영화를 후보에서 제거하지 않는다.

### 4.4 `LocalDraftV11`

```text
draft_version: "draft-v1.1"
draft_id: uuid
editing_festival_id: uuid|null
expected_revision: integer|null
survey_version / catalog_version / rules_version
nickname: string
survey: {q1,q2,q3,q4,q5: 0|1|2|3|4|null, q6: VolumeV11}
selections: category_id -> SelectionSnapshot|null
skipped_categories: CategoryId[]
candidate_order: category_id -> tmdb_id[12]
candidate_page: category_id -> 0|1
pending_selection: category_id -> SelectionSnapshot|null
current_screen / current_category / current_question
updated_at: ISO timestamp
```

별점/CSV 원본/비밀키는 저장하지 않는다. 현재 새 초안1개 + 영화제별 편집 초안만 둔다. 마지막 수정 후7일 만료, JSON 손상·스토리지 비활성화는 안내하고 메모리로 계속한다. 이 경우 새로고침 복원을 보장하지 않는다.

v1.0 초안이 발견되면 **3단계 응답을 5단계로 임의 환산하지 않는다.** 기존 초안은 보존해 확인 가능하게 하고, 새 v1.1 초안에 수상작·닉네임만 복사하며 설문은 null로 시작한다고 알린다. v1.0 앱은 아직 없으므로 이는 호환성 계약이며 현재 마이그레이션 코드를 작성하지 않는다.

## 5. 설문·결과 계약 [반영]

- q1/q2/q3/q5는 실제 경험을 묻는 **빈도5단계**: 전혀 없다0 / 드물다1 / 가끔 있다2 / 자주 있다3 / 매우 자주 있다4.
- q4는 습관의 자기평가를 묻는 **동의5단계**: 전혀 그렇지 않다0 / 그렇지 않다1 / 보통이다2 / 그렇다3 / 매우 그렇다4.
- 화면은 높은 응답→낮은 응답 순서로 표시한다. 기본 선택 없음. 건너뛰기는 별도 null.
- `VolumeV11 = zero | one_to_five | six_to_twenty | twentyone_to_fifty | fiftyone_to_hundred | hundredone_plus | unknown | null`.
- 특별상 후보는 **q≥3**일 때만 된다. 점수 `2*q+bonus`, bonus0/1. q2값(가끔/보통)을 강한 성향으로 승격시키지 않는다.
- 최고 점수→높은 q→고정 우선순위 `interpretation,audience,consensus,secret,credits`.
- 전부null이면 sealed, 나머지 중 후보가 없으면 chair.
- 특별상마다 문구3개. 연결 부문이 있으면 연결 변형, 없으면 q4/ q3 강도에 따른 변형. fallback의 변형도 실제 선정에 따른 조건이다.
- 최종 출력은 특별상 제목+심사평+선정 문장+관람량 문구(선택). 정확한 bonus, 변형 조건, 문구, T01~T18, 가상12명은 SCREEN_CONTENT를 따른다.

동일 입력 정의: 정규화된 q1~q6, 고정 부문 순서로 정렬한 `(category_id,tmdb_id,저장된 title)`와 동일 rules_version. 같은 입력은 동일한 상·문구를 생성한다. 닉네임은 표제 표시만 바꾸며 특별상을 바꾸지 않는다. 수정시각·사용자 ID·후보 배치·CSV 평점은 계산 입력이 아니다.

메타데이터 변경으로 오래된 결과 문구가 바뀌지 않도록 완성 시 스냅샷과 문구를 저장한다. 기존 작품을 다시 저장할 때는 기존 title 스냅샷을 유지하고, 작품을 교체할 때만 새 메타데이터를 반영한다.

## 6. 검색과 CSV

### 6.1 P0 검색 [유지]

TMDB 서버 프록시 사용. `language=ko-KR`, `include_adult=false`. 제목은 trim 후1~100자, 한 글자 영화 검색 허용. IME 조합 종료 후350ms debounce, 이전 요청 취소/요청 ID로 stale 응답 방지.

첫 페이지 최대20개, 최대5페이지 ‘더 보기’. 제목/연도, 동명이작에는 원제 확인. 제목 없으면 원제, 연도 미상 허용, 포스터 없으면 제목 타일. 검색 실패/0건/429/timeout에서 기존 수상작과 후보 페이지 유지. timeout5초, 무한 재시도 금지. 검색 캐시10분, 영화 상세24시간 제안. 사적 결과는 공용 캐시 금지.

검색 결과를 고르는 방식도 UX 테스트에서 선택한 A/B와 동일하다. 공식 API는 원제·번역·대체 제목 검색을 제공하지만, 한국어 검색 품질은 실데이터로 확인한다. [TMDB 영화 검색](https://developer.themoviedb.org/reference/search-movie)

### 6.2 CSV P1 [유지·통합 명세]

실제 파일 형식은 미확인이다. ‘왓챠 공식 연동/원클릭’이라고 쓰지 않으며 개발자 콘솔 코드 실행을 유도하지 않는다.

- 이미 보유한 UTF-8/BOM CSV, 최대2MB/5,000행. Papa Parse, 쉼표 split 금지.
- 제목 필수, 연도/별점/TMDB ID 선택. 사용자가 열과5/10점 척도를 지정한다. 별점은0~5로 정규화, 빈 값은null. 연도1888~현재+2, ID양의정수.
- 깨진 형식·범위 초과 행은 제외하고 행 번호/이유 표시, 정상 행 사용 여부 확인. 빈 별점을0점이나 미관람으로 바꾸지 않는다.
- 중복은 검증 ID 기준; 미매칭은 제목+유효연도 일치, 연도 없으면 완전 동일 원본 행만 제거. 마지막 행 사용, 제거 수 표시.
- 파일/별점은 브라우저 메모리, 매칭할 제목·연도/ID만 서버와 TMDB로 전달. 리뷰는 읽거나 전송하지 않는다.
- ID 상세 확인 또는 정규화 제목/원제+연도 정확 일치+유일 후보를 확인 목록으로 제시한다. 사용자 확인 후 반영. 동명이작/연도 없음/불일치/TV는 수동 확인 또는 제외.
- 동시에2개, 초기 최대60행: 높은 별점30→중복 제외 낮은 별점15→나머지 원본순15. 각 단계가 부족하면 남은 원본순으로60까지 채움. 전부무별점이면 첫60. 이후 요청은 사용자가 선택한 행만 매칭.
- 취소·부분 성공 허용. 새로고침 시 파일 재선택; 이미 확정한 수상작은 로컬에 유지.

부문별 정렬: grand/once는 별점 내림차순; lifetime은 별점 내림차순→연도 오름차순(오래 좋아했다는 뜻 아님); sorry는 매칭 ID를 한 번 섞어 임시 세션에서 유지. dissent는 개인≤2.5·TMDB≥7.5·vote_count≥500, 평점차 내림차순. rescue는 개인≥4·TMDB≤6.5·vote_count≥200, 개인과평균차 내림차순. 일반 동점은 TMDB ID순.

CSV 모드에서는 내 기록 최대4개+기본 후보 최소2개. 부족하면 기본 배열 순으로 보충, 같은 페이지 중복 금지. **2:2:2 가설은 기본 후보 모드에만 적용**한다. 기본 모드의12개 배열/페이지는 따로 보존하고 CSV 끄기·재로드 때 복원한다. CSV 내 새 후보는 다음 미노출 개인 ID와 기본 ID로 구성, 소진 안내. 현재6개 ID와 cursor만 localStorage 보관 가능하나 원본 재선택 전 개인 추천 재생성은 하지 않는다. CSV의 유무·별점만 바뀌고 설문/수상작이 같으면 특별상은 같다.

## 7. 저장·공개·소유권

### 7.1 화면 상태

로컬 작성 → 저장 중 → 비공개 완성 → 공개 동의 → 공개본 생성.

수정 중에는 로컬만 변경한다. 수정 저장 후 공개본은 이전 버전을 유지하며 ‘공유본 갱신’으로 명시적 반영한다. 공개 중단은 공유 행 삭제, 재공개는 새 token. 영화제 삭제는 두 행 cascade. 기존 다운로드 이미지와 외부 SNS 캐시는 회수할 수 없음을 안내한다.

### 7.2 인증과 안내 [유지]

Supabase Anonymous Auth를 첫 결과 저장 직전에 수행하고 세션 재사용. 이메일·비밀번호 입력 UI 없음. 서버는 인증된 사용자를 검증하고, 브라우저 제공 owner_id를 신뢰하지 않는다.

저장 전/내 결과 관리의 필수 안내:

> 이 브라우저에서 수정·삭제할 수 있어요. 브라우저 데이터를 지우거나 다른 기기로 이동하면 편집 권한을 잃을 수 있어요. 공유 링크는 조회용이며 편집 권한을 복구하지 않습니다.

이 한계는 Supabase 익명 사용자 방식의 실제 제약이다. 소유 페이지는 동적 렌더링과 private/no-store로 처리한다. [Supabase 익명 인증](https://supabase.com/docs/guides/auth/auth-anonymous)

인증/CAPTCHA 실패에도 초안은 유지한다. 인증 없는 공유 방문은 가능하다. 세션이 사라진 경우 공유 링크로 자동 새 소유자를 부여하지 않는다. 계정 전환/복구는 P1에도 자동 추가하지 않는다.

Next.js App Router/TypeScript/Tailwind + TMDB + Supabase + Vercel을 유지한다. 버전은 착수 시 안정 버전으로 고정한다.

요청 제한: 10/21에 현재 계정의 관리형 제한/방화벽 기능과 비용 한도를 확인한다. 기본 목표 검색+상세60회/분/IP, 저장10회/시간/사용자, PNG10회/분/IP. 신뢰할 수 있는 플랫폼 IP만 사용한다. 학교 공용 IP에서 오차와429복구를 확인한다.

**관리형 기능 미지원 시** 검색/쓰기 보호를 생략하지 않는다. 시간 예산 내 원자적 Supabase bucket RPC로 보완하고, 원문 IP 대신 HMAC 키·route·window·count·24시간 TTL만 보관한다. 이 작업은 기본 구현이 아닌 위험 발생 시 대체안이다. 보호 확인 전 일반 공개 확산은 보류한다. 메모리 Map을 서버리스 전역 제한으로 부르지 않는다. 익명 가입에는 제공자 CAPTCHA/한도를 설정한다.

### 9.1 최소2테이블

| token | text UNIQUE, 암호학적 난수32바이트 base64url43자 |

후보 배열/페이지/미확정 선택은 로컬 전용이다. DB 결과 변경을 위해 후보 데이터를 업로드할 필요 없다.

### 9.2 쓰기와 무결성

- 서버 입력 최대16KB. 서버와 DB 저장 함수는 category/타입/범위/버전/개수 검증. 새로운 영화 ID는 서버에서 상세 확인, 기존 저장 ID는 스냅샷 재사용.
- `save_festival`: service role만 실행. 서버 검증 owner 전달, create/update 두 동작만. 입력 정규화·결과 계산은 서버, DB는 구조·소유·revision·unique를 확인.
- create의 같은 owner+draft는 정규화 nickname/survey/부문순(category,id)가 같으면 기존 결과를 반환, 다르면409. 메타데이터 갱신시각은 비교 제외.
- update는 소유자 일치+expected_revision일 때만 한 번 저장하고 revision+1. 409면 로컬 보존 후 다시 읽기. 자동 덮어쓰기 없음.
- `publish_festival`: service role만 실행. 본인 원본을 잠그고 expected_revision 검사 후 **잠근 원본 행에서** 허용목록 스냅샷을 구성해 upsert한다. client 제공 public_snapshot은 받지 않는다. 같은 revision 재시도는 같은 token/내용, 갱신도 token 유지.
- 공유 중단은 원본을 잠그는 publish 함수의 `unpublish` 동작으로 직렬화한다. 공개/중단 경합은 잠금 획득 순서대로 처리하며 최신 조회 상태를 UI에 반영한다.
- 영화제 삭제는 owner+revision 조건의 단일 DELETE와 FK cascade. 없는/타인 ID404, 소유자 revision충돌409. 응답 유실 후 재조회404면 삭제 완료로 UI 정리.
- nickname·제목은 일반 문자열로 렌더링하고 HTML 실행 금지. client의 결과문구·owner·URL은 무시한다.

### 9.3 권한

| 주체 | 원본 | 공개 테이블 | 변경 |
|---|---|---|---|
| anon 미인증 | 직접 접근 불가 | 직접 접근 불가 | 불가 |
| authenticated 익명세션 | owner_id=auth.uid() SELECT | 직접 접근 불가 | 직접 테이블/RPC 쓰기 불가 |
| 서버 소유 경로 | 인증 사용자로 읽기 | 소유 확인 후 필요한 행만 | 검증된 owner로 service role |
| 서버 공개 경로 | 접근하지 않음 | token 일치의 public_snapshot만 | 불가 |

RLS on, 테이블 client 쓰기 grant 없음, RPC PUBLIC/anon/authenticated execute revoke. service role은 RLS를 우회하므로 모든 서버 변경에서 검증된 owner 검사 필수. 공개 경로 `select('*')` 금지. 쿠키 기반 변경은 same-origin/Origin과 JSON Content-Type 검사. 로그에 키·쿠키·답변·CSV·token을 남기지 않는다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

최소 보안 증거: 세션A/B/미인증에서 타인 ID를 아는 상태의 조회·수정·삭제·공개갱신·private PNG 거부. 공개 token만으로 수정/삭제 불가. 소유권 상실 시 재소유 자동 배정 불가.

## 11. 이미지·공유·디자인

### 11.1 독립 PNG 경로

HTML 결과를 먼저 저장·읽는다. 이미지 버튼을 눌렀을 때만 별도 생성 API 호출. ImageResponse는 같은 PublicResult로 PNG를 생성하지만 이미지 실패가 결과 API를 rollback하지 않는다.

1080×1920, 결과 상단/최대6개 카드/출처. 렌더링은 Flexbox, 한글 폰트1개, 기본 색/정적 장식. 포스터 timeout3초 후 제목 타일. 외부 fetch는 서버 검증된 TMDB 이미지 도메인만. 3~6부문·긴한글·없는포스터를 시험한다. 폰트/번들 제한은 실제 runtime에서 확인한다. [Next.js ImageResponse](https://nextjs.org/docs/app/api-reference/functions/image-response)

PNG 다운로드가 우선, 파일공유 API는 지원 확인 후 추가. 실패 시 이미지 열기 또는 URL 복사. 취소는 오류가 아니다. R11이 보류되면 실패 버튼을 계속 노출하지 않고 “이미지 저장은 준비 중입니다. 링크로 공유할 수 있어요” 표시.

### 11.2 공유

공개 미리보기에서 “이 내용으로 공유 링크 만들기”. 서버가 공개본만 반환. 내 결과 수정 후 ‘공유본은 이전 내용’과 ‘공유본 갱신’. token은 편집 자격 증명이 아니다.

공개 페이지 no-store/noindex/사이트맵 제외, 개인 페이지 private/no-store. 정적 OG에는 사용자 결과를 넣지 않는다. 공유 중단/삭제 후 공개HTML·PNG404. 외부 플랫폼에 남은 이미지/미리보기 회수 불가.

### 11.3 디자인 토큰 [유지]

종이 #F5F0E6, 잉크 #20201E, 보조 #59564F, 심홍버튼 #8B242D+흰색. 크레용파랑 #315CA8/노랑 #E5B63B는 장식용. 명조제목·고딕UI, 라이선스 확인. 모바일좌우16px, 본문16px/보조14px 이상, 터치44px 이상, 최대본문720px, 포스터2:3, 간격4/8/12/16/24/32/48px.

선택표시는 체크+테두리+텍스트. 키보드/포커스/스크린리더 지원, 대비 실측, reduced-motion. 장식에만 크레용, 본문을 손글씨로 채우지 않는다. 픽셀 테마는 이번에 만들지 않는다.

선택 방식 A/B와 모바일2/3열은 **아직 미확정**. 테스트 전 임시 구현값 B(확정 버튼)+2열. 테스트 방법·출시 선택 기준은 SCREEN_CONTENT 8장이다.

## 13. 기술 검증과 일정

### 13.1 10/21의 세 검증 게이트

| 게이트 | 실제로 확인할 것 | 통과 증거 | 실패 시 |

| G1 익명CRUD |A/B 익명 세션, 본인 create/read/update/delete, 타인 ID 차단, RLS·키 비노출 |브라우저/DB 동작과 거부 테스트 |공개 저장 기능 완료 선언 금지, 10/22 최우선 해결 |

## 14. 검증·과제 기록

- 기능: R01~R10, G1~G3, T01~T18, 후보 복원/2:2:2/페이지, 12가상 사용자 출력, 공개본갱신, 권한, 360px.
- 사용자: 친구2~3명 테스트는 실시 전. 관찰 없는 UX효과·친숙도·재미·시장성 통계는 기록하지 않는다.
- 실제 테스트 로그: 기대/실제/재현/AI요청 원문·요약/수정/재확인/남은한계/commit. 목업과실API, 데스크톱에뮬레이션과실폰을 구분한다.
- 보고서: 실제 앱URL, GitHubURL, 소개, 주요화면, 데이터흐름, 실제 AI 문제해결. PNG/CSV가 미완료면 숨기지 않는다.
- v1.0은 원문 보존. v1.1 승인 후 docs4개를 해당 버전으로 고정하고 이후 변경마다 CHANGELOG에 이유·영향 기록.
